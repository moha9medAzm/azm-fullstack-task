# 07 — Assumptions & scope

## Why the scope was cut

The brief lists **12 feature areas**. Building all 12 in the available time means
none is production-shaped: no real validation, no audit trail, no tests, no error
contract. The assessment rewards *engineering foundations, testing, security and
edge cases, ownership* — none of which a broad-but-shallow build demonstrates.

**Decision:** implement the **core support loop** (5 areas) end-to-end and
correctly, and write down the rest as explicit, revisitable out-of-scope items.

---

## In scope (built, tested, documented)

1. **Customer Management** — profiles, contact details, notes, per-customer
   interaction history.
2. **Ticket Management** — CRUD, categories, priorities, a validated status
   lifecycle, assignment, escalation, an immutable history.
3. **Agent Dashboard** (core) — my open tickets, queue counts by status/priority,
   SLA-breaching and unassigned lists, deep links into filtered views.
4. **SLA & Automation** (core) — priority-driven response/resolution targets,
   read-time breach derivation, manual + automatic escalation, alerts surfaced as
   dashboard lists.
5. **Security & Administration** (core) — users & roles (ADMIN/AGENT), JWT auth,
   server-side RBAC on every route, full ticket audit log.

---

## Out of scope (with rationale and a path back in)

| Area | Why deferred | Path back in |
|------|--------------|--------------|
| **Communication channels** (Email / WhatsApp / SMS / live chat / web forms) | Each is an integration project (inbound parsing, delivery, retries, webhooks). `channel` is a field on the ticket so the data model is ready. | Add an outbound provider adapter + an inbound webhook that creates/*appends* to tickets. |
| **AI features** (summaries, suggested replies, auto-categorisation, chatbot) | Needs the ticket/knowledge corpus first; not core to the loop. | One feature end-to-end via the Claude API (e.g. summary + suggested reply on the detail page). |
| **Customer portal** | Different auth model and surface; agents-first was the priority. | Add a `CUSTOMER` role, portal routes, and reuse the same ticket API with row-level scoping. |
| **Knowledge base** | Standalone content domain. | `Article` entity + search; link articles from tickets. |
| **Reports / BI / exports** | Dashboard stats cover the operational need; BI is a separate concern. | Aggregate endpoints + CSV export + a charts page. |
| **ERP / external integrations** | No target system in this exercise. | Typed integration adapters behind a queue. |
| **File attachments** | Storage + AV scanning + access control is its own slice. | `Attachment` entity + object storage + signed URLs. |
| **Multi-branch / multi-department / multi-tenant** | Single workspace keeps the model legible. | Add `workspaceId`/`departmentId` scoping + tenant middleware. |
| **i18n / Arabic / RTL** | English-only to focus on behaviour. | `react-i18next` + a `dir` switch + Arabic catalog. |
| **Email / push / websocket notifications** | The dashboard's breaching/unassigned lists are the MVP "alerts". | A notifications service + a channel adapter; websocket for live updates. |
| **Self-service signup** | Support staff are provisioned by an admin. | `POST /auth/register` gated by an invite token. |

## Assumptions

| # | Assumption | Consequence if wrong |
|---|------------|----------------------|
| AS-1 | **Wall-clock UTC** SLAs — no business-hours calendar. | Targets tick over weekends/nights. Fix: a working-calendar function feeding `computeSlaDueDates`. |
| AS-2 | Users are created by an admin or the seed; **no public signup**. | Add an invite/registration flow. |
| AS-3 | The SLA sweep runs **in-process** on `setInterval` (plus a manual admin trigger). Fine for a single instance. | For multi-instance, move to an external scheduler / job runner with a lock. |
| AS-4 | **SQLite** is acceptable for the exercise. | Swap `provider` to `postgresql` and re-migrate — no app-code change ([ADR-0001](adr/0001-stack-and-database.md)). |
| AS-5 | `reference` (`TKT-NNNN`) is generated by counting existing tickets inside a transaction. Adequate at this scale; a high-concurrency writer could race. | Move to a DB sequence / dedicated counter row. |
| AS-6 | Ticket-list free-text search is **case-sensitive** (`contains` on SQLite; Prisma has no `mode: 'insensitive'` for SQLite). | On Postgres, add `mode: 'insensitive'`; or store a lowercased shadow column. |
| AS-7 | One agent-facing SPA; **no customer-facing surface**. | See "Customer portal" above. |
| AS-8 | Frontend/backend types are **mirrored by hand** (`web/src/api/types.ts`), not shared via a package. | Extract a `packages/shared` workspace or generate types from Zod/OpenAPI. |
| AS-9 | An `AGENT` may assign a ticket to **any** agent (not only themselves). | Tighten `assignTicket` if self-assign-only is required. |
| AS-10 | Escalation raises priority by **exactly one level** and recomputes the resolution SLA (same as manual escalate). | Make the step configurable per policy. |
